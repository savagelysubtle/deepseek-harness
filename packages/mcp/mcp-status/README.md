# @deepseek-ai/dsh-mcp-status

English | [中文](README.zh.md)

Permanently-mounted Remote status registry for every active [`@deepseek-ai/dsh-mcp-client`](../mcp-client/README.md) connection. `McpStatusRegistryService` registers the `mcpStatus` service and publishes four Remote methods under the `mcp` namespace — `mcp/status` (list), `mcp/authorize-start`, `mcp/reconnect`, and `mcp/set-enabled` — plus the `mcp/status-changed` push event. See [`docs/subsystems/mcp.md`](../../../docs/subsystems/mcp.md) for the full wire contract.

## Why this is its own package

This service used to be mounted lazily, once per `ctx.root`, the first time any `@deepseek-ai/dsh-mcp-client` instance activated. That was correct at the Cordis fiber level — the mount outlived any one instance's own disposal — but wrong one layer up: `@deepseek-ai/dsh-typert-loader` registers and withdraws a package's strict Typert manifest keyed to a *Loader entry*, and the service had none of its own. Disabling the last live mcp-client server withdrew its registration too, and the Gateway's strict/SRC-fallback latch is one-way — once a strict registration for an endpoint has ever existed, SRC fallback is permanently forbidden for that endpoint, even though this (still-alive) service could have answered it.

The fix is this package: it carries its own permanent Loader entry (mounted in [`packages/bundle/web-app/cordis.patch.yml`](../../bundle/web-app/cordis.patch.yml) beside the other host services), so the Typert registration is keyed to an entry that never unmounts — entirely decoupled from any individual mcp-client server's lifecycle. `@deepseek-ai/dsh-mcp-client` itself keeps only a root-scoped handle store that every instance registers into unconditionally; a host with this package absent from its `cordis.patch.yml` (headless, embedded) behaves identically, minus the Remote surface itself.

## Behavior

- `mcp/status` lists every registered server's current status, plus a synthesized `disabled` row (no live handle) for every other mcp-client mount the profile's `cordis.patch.yml` marks disabled — a Tools panel can always show a re-enable action for a server it just disabled.
- `mcp/authorize-start` begins (or resumes) one server's OAuth consent flow: probes reachability, binds the shared loopback listener, and returns the consent URL. The listener is single-flight across every server, not per-server.
- `mcp/reconnect` manually retries a given-up or disabled server now.
- `mcp/set-enabled` persists a plugin mount's enabled flag via an atomic `cordis.patch.yml` read-modify-write, matched by `config.serverName` — never the mount's opaque `id`. It parses the file as a CST-preserving YAML `Document` (via `@deepseek-ai/dsh-mcp-client`'s `parsePatchFile`, which registers a custom `tag:yaml.org,2002:js` scalar tag so the boot loader's `!!js` token-header dialect — a template expression like `Authorization: !!js '`Bearer ${process.env.TOKEN}`'` — round-trips instead of warning or being dropped), edits only the target entry's `disabled` flag in place via `doc.setIn`, and re-serializes with `doc.toString({ indent, indentSeq, singleQuote: true })` — `indent` and `indentSeq` inferred from the file's OWN existing formatting (a small line scan over the original text; `yaml`'s own `Document` exposes no API for "what indentation did this file use") rather than a fixed convention, so a profile written with `yaml`'s own default `indentSeq: true` style or a 4-space indent round-trips just as losslessly as the real `web-stable` profile's own 2-space, `indentSeq: false` `insert:` lists. Every other tag, every comment, and the rest of the file's formatting survive the write untouched, including its own line-ending convention: a CRLF file is written back CRLF throughout, and a file with no final trailing newline is written back with none either, because `yaml`'s own serializer always emits bare `\n` with exactly one trailing newline no matter what the source looked like, so `set-enabled` converts its output back to the original's convention before ever comparing or writing it (a file that mixes both conventions in different places may still be refused, for the same reason as any other unprovable difference). If the matched entry turns out to be a YAML alias or anchor reference rather than a plain mapping — invisible to the matching step, which works off the fully-resolved document — the in-place edit cannot be applied at all, and the write is refused with `mcp set-enabled: cordis patch file "<path>" entry for "<serverName>" is not a plain mapping the host can edit in place (YAML alias or anchor reference) — edit the file by hand and restart the host (SWD-170)`. Before committing an edit that CAN be applied, the method proves two separate things about the result: first its SHAPE, by diffing the rewritten text against the original — the only difference the write is allowed to introduce is one added, removed, or changed `disabled:` line within the target entry, and any other difference refuses the write outright (nothing is written), logging the real file path to the host log via `ctx.logger.warn` and returning an error naming the first unexpected differing line and the remedy, with the path itself redacted on the wire: `mcp set-enabled: cordis patch file "<path>" could not be rewritten without altering other content (first unexpected difference at line N) — edit the file by hand and restart the host (SWD-170)`; and second its LOCATION, by re-parsing the rewritten text and re-matching it by `config.serverName`, confirming the `disabled` flag now reads the expected value on that exact mount's own entry, not merely that some line somewhere changed in the right shape.

The service is Remote-only and deliberately declares no same-process Cordis `Context` merge. Client packages consume it through the explicit [`api-remotes`](../../api/remotes/README.md) assembly rather than importing the Host implementation.

## Model Experience

None, as this Host-only status registry registers no prompt, tool, message, or provider request.

#### KV Cache effect

None; this package never assembles model input.

## Known Limitations and Deferred Work

- **The consent loopback listener is single-flight** — only one `authorize-start` flow may be pending at a time across every registered server.
- **No provenance or history beyond the current patch file and live handles** — `set-enabled` never inserts a new mount, and `list()` reports only what the handle store and the current `cordis.patch.yml` say right now.
- **The `indent`/`indentSeq` inference is a best-effort heuristic, with the lossless-rewrite verification as its real backstop** — it uses only the FIRST example of each kind found anywhere in the file (the first key with a nested mapping for `indent`, the first key with a nested block sequence for `indentSeq`), so a file that mixes two different indentation conventions in different places could still be inferred wrong for whichever part the edit lands on; either way the write is never silently corrupted — a wrong inference simply trips the single-line-diff check and refuses, exactly like any other unexpected difference (SWD-170 round 1 resolved the prior SWD-169 refusal-on-any-unsafe-tag guard with this lossless writer and verification; round 2 replaced its initial hardcoded `indentSeq: false` with this per-file inference).
