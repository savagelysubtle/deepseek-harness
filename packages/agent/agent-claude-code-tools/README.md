# @deepseek-ai/dsh-agent-claude-code-tools

English | [中文](README.zh.md)

The **permission policy core** for [Claude Code seats](../agent-claude-code-driver/README.md). It turns host-private inputs (the host seat's policy fields, the working directory, the seat name; never a registry row) into the rulebook one seat runs under: permission rules, a second-layer `PreToolUse` hook, and the file that hook reads. The package is also the cordis plugin that serves it to the driver as `ctx.claudeCodePolicy`, together with the per-seat `dsh` MCP tool server (`mailbox_send`, `mailbox_directory`); see below. The contract types it implements live in the driver (`policy-contract.ts`).

## What it generates

- **Rules** (`generateRules`). Claude Code path rules are gitignore-style: `//abs` is an absolute path, `/abs` is project-relative, so every rule here is emitted as `//` followed by the path without its leading slash (for example `Read(//home/steve/x/**)` for the cwd `/home/steve/x`; never `///`, and the `~/` form is not used). Each protected directory gets both the bare entry and the `/**` entry, because a worktree's `.git` is a file. Only `Read(...)` and `Edit(...)` are real path specifiers (`Read` covers Grep and Glob; `Edit` covers Write, MultiEdit and NotebookEdit), so no `Write(...)` or `Grep(...)` rule is emitted. Every role gets the same deny set: `~/.claude/**`, `~/.claude.json`, `~/.ssh/**`, `~/.config/gh/**`, `~/.dsh/**`, `~/.agents/**`, and inside the cwd `.git/**`, `.claude/**`, `.mcp.json`, `.husky/**`. A `coder` also gets `Read` and `Edit` allow rules for `//<cwd>/**`; a `lead` gets no native tool at all.
- **A cwd or home that cannot be written into a rule is refused** (`UnsafePathError`): not absolute or not normalised, the filesystem root, containing any of `* ? [ ] ! # { } \ ( )`, whitespace or a control character, not equal to its own realpath, not a directory, or (for the cwd) inside one of the protected home locations.
- **Settings** (`generateSeatPolicy`): `{settings, allow, disallowedTools, tools, fences}` where `settings` holds the guard hook plus `permissions.deny`, `allow` holds `mcp__dsh__<name>` entries (and the cwd `Read`/`Edit` rules for a coder), and `fences` repeats `dontAsk`, `settingSources: []`, `strictMcpConfig: true`. Only the SHA-256 of the result (`settingsSha256`) is meant to be logged. There is no `canUseTool`: it is never called under `dontAsk`, so the hook is the second layer.
- **Tools.** The lead template is exactly `mailbox_send` and `mailbox_directory` (as `mcp__dsh__mailbox_send` and `mcp__dsh__mailbox_directory`). The host seat's `tools` list cuts the template down; a seat left with no tool throws `SeatMutedByPolicyError` from the driver contract. Later slices append names and hook groups through `ContributorRegistry.registerToolContributor` and `registerHookContributor` without editing this package.
- **Readiness** (`ReadinessRegistry`). `lead` is servable as soon as the policy service exists. `coder` is servable only when contributors providing `sandbox`, `canary` and `rules-hooks` have all registered; `missing` names what is absent.

## The dsh tool server and the provider

The package is also a cordis plugin (`name: agent-claude-code-tools`, config `policyDir`, optional `home`, `nodePath`, `guardPath`, `allowedCwdRoots`). Mounting it registers the `claudeCodePolicy` service the driver reads at use time, so it may mount before or after the driver. Per query (`extend`) the provider:

1. refuses a `mail-only` seat, and a role the readiness registry cannot serve;
2. pins the seat's working directory: when `allowedCwdRoots` is set, a `cwd` outside every root (compared lexically by whole path segments, so the roots must be canonical paths; an empty list refuses every seat) throws; the first query then fixes the `cwd`, and any later query whose `cwd` differs by even one character throws;
3. checks the host stanza's `tools` against the tool template and the policy template, and mutes the seat (`SeatMutedByPolicyError`, naming every missing name) before anything is written;
4. attests the node binary and the guard script (re-checked on every query), generates the seat's policy once per seat, cwd and host fields, and rewrites the policy file atomically when it is missing or changed on disk; a write failure throws and the driver leaves the mail queued;
5. runs `verifyGuardCommand` on the exact hook command the first time it sees a node, guard and policy hash combination, and throws on failure, so a guard that cannot start (which would fail open) never gets a server handed out;
6. returns `{settings, mcpServers: {dsh}, allow}` with a fresh server for this query. `allow` is exactly `mcp__dsh__<name>` for each exposed tool (plus the cwd `Read`/`Edit` rules for a coder) and nothing else, because the driver fails a turn whose CLI-reported tool list differs. The driver itself switches auto-memory off; the provider does not return that setting.

The server (`createSeatMcpServer`) is the SDK's in-process server named `dsh`, one per seat per query. Every tool is built over its own closure (the seat's own agent id, `send_to`, `allow_blocking`, the live taint and delivered-trace controls), so two servers never share state. Input schemas are strict zod objects: an unknown key (`from`, `seat`, `tainted`, `chain`, anything) is rejected by the SDK layer before the handler runs, never stripped. Every schema is converted to JSON Schema at construction and must come out as a closed object; one that cannot convert throws then, not at call time. Every string a tool returns goes through the scrubber (control characters other than newline and tab removed, any path under the operator home or the seat cwd replaced by `[path]`, length capped at 4000). A tool can narrow that per call: `context.scrub(text, {scrubRoots, maxLength})` (and the matching fourth argument of `textResult`) takes `scrubRoots` of `'home'` and/or `'cwd'` (default both, the mailbox tools' behaviour; at least one is required, an empty list throws; the bash tool passes `['home']` because it runs at the real cwd) and a `maxLength` (a positive safe integer of at most 1 MiB, otherwise it throws). When `'cwd'` is not a root and the cwd sits under the home, paths inside the cwd are left intact (the model already knows its cwd, and redacting it would break tool agreement for clones under the home) while every other path under the home is still redacted. The closure also carries the seat's `cwd`, fixed at construction, and a handler receives the MCP call's abort signal as its second argument.

**Every tool declares its taint.** `taint: 'always' | 'never'` is required on every tool (`defineSeatTool` and `createSeatMcpServer` reject a declaration that is missing or not one of the two, naming the tool), and a `'never'` tool must also carry a non-empty `taintReason`. `createSeatMcpServer` is the only place a handler is called: for an `'always'` tool it marks the session tainted (`tool:<name>`) before the handler runs, so a throw or a timeout after the handler read content still taints. Tools never call `markTainted` themselves. `tests/mcp/taint-registry.spec.ts` snapshots every `'never'` tool with its reason (and, by a textual scan of `packages/*/*/src` and `apps/*/src`, the source files that declare one; a taint given through a constant is flagged for manual review), so adding one shows up as a diff. `neverTaintTools(server)` returns `name -> taintReason` for the `'never'` tools a server really serves, so the snapshot can run against the full registries. The "no path to a handler" test is a textual tripwire over the files that import this package, not a proof: `SeatToolTemplate.build` and `SeatTool.handler` are public, so code that builds a tool can still call its handler directly and skip the taint step. The server also reads each tool's `taint` and `name` once at construction.

The lead template is exactly `mailbox_send` and `mailbox_directory`. The host stanza's `tools` must be a subset of it (an unknown name, or an empty list, mutes the seat). `check_inbox`, `await` and tracker tools are not offered: mail is delivered by the driver, and deferred-result machinery belongs to S6. S6 and S7 append tools by registering a factory on a `SeatToolTemplate` and a name on the `ContributorRegistry`, without editing S5 files.

### `mailbox_send` rules

- **(a) Identity.** `from` is the seat's own mailbox agent id captured when the server was built. It is never read from input and is never the Claude session id.
- **(b) Destination.** The message goes to `to` and nowhere else, and `to` must be in the host stanza's `send_to`. An empty `send_to` refuses every send with a reason naming the stanza key `send_to`.
- **(c) Reply label.** `replyToTraceId` is accepted only if it is in the set of trace ids the driver reports as delivered to this seat. It is a label copied onto the outgoing message as its trace id; it is never used to find a destination (there is no trace lookup and no trace-based routing). An unknown trace id is refused.
- **(d) Blocking.** `blocking: true` is refused unless the host stanza sets `allow_blocking: true`.
- **(e) Taint.** A send from a tainted session carries `tainted: true` and no `chain`: `from` already names the origin, and the bridge appends each hop to `chain` itself. **Stamping labels the message; it never denies the send.** An untainted session asserts nothing (absent means not asserted, never clean). Both mailbox tools declare `taint: 'never'` because they return only operator-configured names and a trace id; any tool that returns mail bodies or other external content declares `taint: 'always'`.
- **(f) Validation.** The message is published through the mailbox service (`ctx.mailbox.publish`, looked up at send time), which applies the mailbox publish validation. A rejected publish comes back to the model as a fixed error result (the mailbox's own text is logged host-side only), not a throw.
- **(g) Result text.** Short, scrubbed, and it names only the seat that was mailed (`Sent to <to>. Trace id <id>.`).

The body is capped at 64 KiB of UTF-8 (the mailbox packages declare no limit of their own, so this package sets one). One server (one query) may send at most `MAX_SENDS_PER_TURN` = 20 messages; the 21st is refused with a reason naming the cap, and refused sends do not count toward it.

### Readiness story

A `lead` needs nothing beyond this plugin. A `coder` needs contributors providing `sandbox`, `canary` and `rules-hooks`; `sandbox` comes from the S6 bash plugin, `canary` and `rules-hooks` from S7, which does not exist yet, so a coder policy still reports not-ready (`missing: canary, rules-hooks` once `sandbox` is registered) and the driver refuses the seat at create with the missing names. No contributor is faked.

## The seat-guard hook

`src/bin.ts` is a thin reader, bundled with the guard modules into one plain-JavaScript file, `lib/seat-guard.js`, that ships in the package (`guardScriptPath()` returns it; Node refuses to strip TypeScript under `node_modules`, so the `.ts` source is only usable inside the workspace and `buildHookCommand` rejects it unless `allowSourceGuard` is set). `verifyGuardCommand(command)` runs the exact generated command with a payload the policy must refuse and requires exit code 2 with the guard's own `seat-guard: denied` reason; call it before a seat's first query. The host writes `<policyDir>/<seat>.json` atomically (temp file in the same directory, fsync, rename; `writePolicyFile`) and gets back the SHA-256 of the exact bytes. The hook command line is built by `buildHookCommand`:

```
/usr/bin/env -u NODE_OPTIONS <attested node> <attested guard script> --policy <path> --sha256 <hex> --seat <name>
```

The `env` is the absolute `/usr/bin/env`, attested like node, and never found through PATH (the SDK has no per-hook environment, so the command line is the only place to pin it). The hook does not run the package's `lib/seat-guard.js` directly: the provider copies it to `<policyDir>/seat-guard.js` (mode 0500, in a directory that must be mode 0700 and owned by the host user; an existing directory with another mode, owner or a symlink is refused with the remedy), attests the copy against the source hash and builds the command with the copy's path. The copy is rewritten only when its hash or mode differs, and always from the source pinned at first use; a source that changed since is refused (`restart the host`), never copied, so a tampered package file cannot reach a seat.

Every value is checked against a strict grammar (seat `^[a-z][a-z0-9-]{0,31}$`; paths absolute, canonical, no shell metacharacters) and single-quoted; the timeout is 60 seconds. `attestFile` verifies the node binary and the guard script before the command is built: regular files, owned by the operator or root, not group- or world-writable, in a directory chain nobody else can write, SHA-256 pinned. It mirrors the driver's `attestClaudePath` rules because that function refuses script extensions and is not parameterised; the hash helper is the driver's own.

The hook reads the `PreToolUse` JSON on stdin and checks `tool_input.file_path`, `path`, `notebook_path`, the Glob `pattern` and the Grep `glob`. For every candidate it resolves the real path (parent plus basename for a new file, nearest existing ancestor for a deeper one) and requires it to sit inside the policy's roots by whole path segments (`/a/b` is not inside `/a/bb`), outside the protected prefixes, and not an existing file with more than one hard link. `..` anywhere, a leading `~`, symlink escapes, dangling symlinks and absolute paths outside are denied. The policy file is read only if it is a regular file of at most 64 KiB and the hook payload is capped at 1 MiB. Glob and Grep patterns may not start a new path inside a brace or extglob group (`{/etc/x,y}`, `@(/etc/x|y)`) nor hold a `/` inside one. Unless the policy sets `denyDirsContainingProtected: false` (an optional flag on the v1 file, default on), a Grep or Glob whose effective search directory lies above an existing protected location (so `Grep` over the cwd of a git checkout) is denied: search a subdirectory. A tool outside the policy's `tools` list is denied, and an `mcp__` tool must be named in it.

**The hook only ever denies.** A deny is exit code 2 with a one-line reason on stderr. A pass is exit code 0 with no output at all; the hook never prints an allow decision, and a static test asserts the hook sources contain no such output path. It also denies when the policy file is missing, unreadable, corrupt, has `v` other than 1, names another seat, or its SHA-256 differs from the one on the command line. The matcher string in the generated hook entry (`Read|Edit|Write|MultiEdit|NotebookEdit|Grep|Glob|mcp__dsh__.*`) is covered by a unit test against every native file tool.

## Tests

`tests/` uses real temporary directories (symlink out of the cwd, hard link, `..`, `/a/b` against `/a/bb`, glob-character cwd, new-file parent checks) and runs the hook as a child process on stdin fixtures. The provider and tool specs (`tests/provider.spec.ts`, `tests/mcp/**`) call the tools through the SDK server's own request handler so its input validation runs, publish into a real SQLite mailbox, and run the real guard proof (see the limitation on the built guard). Per-file 100% coverage is enforced by the repository coverage gate.

## Known Limitations and Deferred Work

- **The hook fails open on a crash, timeout or missing node.** Only exit code 2 blocks a call in Claude Code. The guard catches everything it can and exits 2, but a killed or absent process cannot; the boot canary of a later slice (S7) is the structural catch, which is why `coder` stays refused until it exists.
- **A Rust port of the guard** (compiled, no Node startup cost per tool call) is a tracked follow-up; today it is Node running `lib/seat-guard.js`.
- **Hook-to-tool race.** The check-then-use window between the hook and the tool is inherent to hooks, and hard-link detection only sees links that already exist.
- **Symlink-following by the tools.** Whether ripgrep and the glob tool follow a symlink planted inside the cwd (for example a pattern `lnk*/*`, which the guard judges only by its static prefix) is pinned by the live probe, not by unit tests.
- **Provisioning is part of the trust boundary.** The clone a coder works in must be provisioned by the host; a coder can still edit files that run later (`package.json` scripts, `lefthook.yml`), which lands on human review.
- **Contributor hook groups are not validated.** `ContributorRegistry.extraHookGroups` returns whatever S6/S7 contributors register; those slices must audit what they add.
- **Case-insensitive filesystems are refused** when a protected entry also answers to its upper-case name, and a cwd equal to the home directory or inside a protected home location is refused.
- **Rule matching is not provable offline.** The SDK exports no permission evaluator, so the generated rule strings are proven against the real CLI only by the live probe of the slice; the hook is the layer unit tests can fully exercise.
- **A path guard cannot see the shell.** Native `Bash` is disallowed; the shell sandbox is a later slice.
- **Pattern characters in a cwd are refused, not escaped.** Move the work to a path without them.
- **The guard is a build output.** `lib/seat-guard.js` is gitignored and produced by `pnpm run typecheck` (or the package build). A provider whose guard file is missing never returns an extension (the attestation refuses it); tests that exec the guard build it first when it is absent.
- **A coder policy is not-ready until S7.** The `sandbox` contributor registers through `claudeCodePolicyRegistries`; `canary` and `rules-hooks` do not exist yet, so the report stays `missing: canary, rules-hooks` and the driver refuses the seat. Readiness keys on the `provides` string, not on who registered, so a second contributor claiming `sandbox` changes nothing (tests pin both). Nothing here fakes a contributor.
- **The registries are shared through a service, in either mount order.** `claudeCodePolicyRegistries` is `{readiness, contributors, tools}`, the same instances the policy uses. A later plugin that lists `claudeCodePolicyRegistries` in its `inject` is started once the provider is mounted, whichever mounts first. Registering a tool takes two steps: a factory on `tools` and the name on `contributors` for the roles that may have it (a name in only one of them mutes the seat with the missing name).
- **Taint stamping labels, it does not deny.** A manipulated tainted session can still send within its `send_to` list.
- **Tool results are text and scrubbed.** Paths under the operator home or the seat cwd are replaced by `[path]` (a tool may choose `home` only); other paths pass through.
- **The policy directory is denied to file tools.** `generateRules` and `generateSeatPolicy` add the (canonical) policy directory to the deny rules and the policy file's denied prefixes, so the policy files and the 0500 guard copy are unreadable and unwritable by rules even when the directory sits under a seat root; a cwd that equals the policy directory, is inside it, or CONTAINS it is refused (`extend` names both paths before pinning anything), because the bash sandbox binds the whole cwd read-write, which would make the policy files and the guard copy writable from the shell. The 0500 copy alone does not protect against a same-uid writer.
- **Handlers run in the host process** with the host's authority, taking model-controlled arguments; strict schemas, closures instead of arguments and the `send_to` list are the only fences.
- **The hook's node and every parent directory must not be writable by others.** `attestFile` always refuses a world-writable file or directory (a sticky directory such as `/tmp` is allowed in the chain). A group-writable bit is accepted only when the group is the owner's private group, read straight from `/etc/passwd` and `/etc/group` (no NSS): the owner is the running user or root, the group has the same name as the owner's passwd entry, its member list is empty or the owner alone, and no other passwd entry has that group as its primary group. This is what an fnm install needs (its version directory is mode 775 with the owner's private group). If either database cannot be read or the user is not found there (LDAP or other NSS accounts), the strict rule applies and the operator runs `chmod g-w`. The driver's own `attestClaudePath` is unchanged. The live probe's case 0 prints the refusal text.
- **The guard file's mode is pinned by the build.** The tsdown `onSuccess` step sets `lib/seat-guard.js` to 0644, because a 664 file (umask 002) is refused by the same attestation; a test asserts the built file is neither group- nor world-writable.
- **Observed in the live probe: a hard-linked file inside the cwd is denied only by the guard.** The CLI's own rules read it; if the hook fails open, nothing else stops that read.
- **Observed in the live probe: Glob `lnk*/*` is denied by the guard only because the search directory contains `.git`.** In a non-git cwd the guard does not deny the pattern (it judges it by its static prefix); the CLI returned no files for it.
- **Observed in the live probe: an `mcp__dsh__` tool the server exposes but the allow list omits still appears in the init tool list** and is denied by the guard only. The provider therefore builds the server from the allowed tools only (`policy.tools`), so the exposed set and the allow list are the same set.
- **A mailbox rejection reaches the model as a fixed sentence** (`mailbox_send refused: the mailbox rejected the message`); the mailbox's own text goes to the host logger only.
- **The proof run blocks the host for up to 15 seconds.** `verifyGuardCommand` is synchronous because the driver's `extend` is (a frozen contract); it runs once per guard, node and policy hash, and the guard answers in well under a second. Making it asynchronous needs a driver contract change and is left to a later slice.
- **The policy cache is keyed on the registries.** A contributor, hook group or tool registered after a seat's policy was cached bumps a version counter and the next query regenerates the policy. The on-disk check opens the policy file without blocking and reads it only if it is a regular file of at most 64 KiB.
