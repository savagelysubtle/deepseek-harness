# Agent Note: mailbox_await — the deadline wait primitive

Status: implemented

English | [中文](2026-08-29-mailbox-await-tool.zh.md)

## Problem

`blocking` on a mailbox message is a label, not a mechanism: the seam shipped exactly two model-facing tools — `mailbox_send` and `mailbox_check_inbox` — and no wait at all. A seat told to hold its turn for a reply therefore improvised a Bash sleep-poll loop, burning one turn per poll, and hung forever when no reply ever came. Observed live: seat A sent a blocking message to seat B, B was stopped mid-reply, and A polled past 2m27s with no reply, no error, and no timeout.

The store already recorded everything the wait needed to know — a settled lease's `deliveredAt`, and (from the refusal-notice work) a refused row's terminal `failureReason` reachable through `lookupByTraceId` — but nothing read it on the sender's behalf while that sender sat blocked.

## Decision

`mailbox_await` is the third tool on the same mount, built by the same `mailboxAwaitTool(mailbox, identity)` pattern and resolved through the same `resolveMailboxIdentity`/`callerIdentity` identity path — there is no second identity mechanism.

- **Correlation rides `traceId`, and replies thread it.** `mailbox_send` mints a fresh correlation id per send, stores it on the row, returns it in `SendResult`, and renders it into the result text, so the model holds the handle. The await's `traceId` argument names that id; `lookupByTraceId` retrieves the row's fate. Direction selects the sent row: the entry whose recorded `from` equals the calling seat's own address — a shared id also names reply rows and bounces, which are inbound. The send schema carries `replyToTraceId`: publishing a reply under the awaited send's id threads it onto that chain (the same threading the bounce path uses), which is what lets a traced wait match THE reply instead of any inbound mail.
- **Reply detection reads; the claim is the fallback.** Each tick reads before claiming. The bridge — the normal delivery path — claims a reply, steers it into the waiting seat's live turn, and settles it `done`, and any reply faster than the awaiting seat's model round trip loses the claim race deterministically (measured 1.9 s reply against a 3.4 s await start), so claim-only detection timed out on every fast reply while the answer sat in the conversation. `detectArrivals` reads what the claim can no longer see: a traced wait prefers trace-carrying rows addressed to it in `done`/`claimed` state, falls back to any inbound mail admitted since the awaited send (an unthreaded reply still ends the wait; unrelated inbound mail does too), and an untraced wait reads inbound mail since the wait began. Reads claim and settle nothing — a `done` row stays the bridge's delivery, a fresh `claimed` row stays in its holder's lease — so the same reply can reach the model twice (steered turn and tool result), the seam's existing at-least-once property.
- **A refusal breaks the wait.** Each tick reads the traced row before claiming; `state: 'failed'` ends the wait immediately with the recorded reason verbatim (or a stated fallback when the envelope is unreadable). A refused send never waits out the deadline — the refusal was known seconds in, and the full five-minute hang is exactly what this tool exists to remove. Unrelated mail queued behind the refusal stays pending for the next drain.
- **A timeout states what is known.** Expiry returns an ordinary result, not an error, carrying `sentState`: `delivered` (with the row's `deliveredAt`), `claimed` (picked up, delivery unsettled), `pending` (never picked up), or `unknown` (no `traceId`, or no row this seat sent). "Timed out, delivered 4 minutes ago" and "timed out, never delivered" demand different responses, and the result gives the model both facts plus `waitedMs`.
- **All deadline arithmetic runs on the host clock.** `clampAwaitDeadlineMs` resolves the requested deadline to the 1000–600000 ms range (default 300000) at execute time; the caller never supplies a remaining budget. The floor exists because a wait shorter than one poll interval cannot observe a mid-wait arrival; the ceiling keeps one held turn bounded and every expiry returns the decision to the model. The tool declares no `timeoutMs`, matching its siblings — its own clamped deadline is the bound.
- **Poll, not busy-loop.** One 2 s sleep between ticks — below the bridge's own 5 s drain cycle, a handful of cheap SQLite statements per tick. Without a `traceId` the wait ends on any inbound mail for the seat and reports `unknown` on expiry.
- **The queued claim stays.** Mail still `pending` for the seat is drained exactly as `mailbox_check_inbox` does — claim, settle every receipt `done`, return the same entry shape and rendering — which also keeps the single-seat headless world working, where the tool is the only reader and no bridge ever pre-empts a row.
- **Cancellation.** The wait forwards `exec.signal` into every store read and its sleeps; a sleep rejects with the abort reason and clears its timer, so a stopped seat reclaims control in milliseconds and the registry's cancellation contract reports the call.

## Alternatives considered

- **Claim-only reply detection** — rejected after the user-level test failed live: the bridge wins every reply that lands before the await's first poll, deterministically, and a settled row is invisible to a claim. Read-based detection sees the row whatever consumer won it; the claim remains for mail still queued and for the no-bridge single-seat world.
- **Requiring the thread as the only correlation** — rejected: detection must not depend on the peer's cooperation, so a reply published without `replyToTraceId` still ends the wait through the inbound-since fallback. Threading is the precision layer on top, not the gate.
- **Fusing an abort-with-timeout signal (`deadline()`) around each tick** — rejected: the wait owns no timeout classification, because deadline expiry is a result, never an error; a plain timer plus abort listener is the smaller mechanism with the same cleanup guarantee.
- **Reporting `claimed` as "never picked up"** — rejected: the store distinguishes picked-up-but-unsettled, and reporting it as pending would misdiagnose a slow transport as a dead one. It ships as its own `sentState`.

## Consequences

The send tool's model-visible schema grew `replyToTraceId`, and its result and rendering carry the correlation id — which for a threaded reply is the awaited send's id rather than a fresh one. A threaded conversation accumulates hops on ONE chain, so the bridge's per-trace admission cap (default 8) bounds a thread's length, and the refusal names the trace when it trips; a longer correspondence re-threads onto a fresh send. The wait returns a reply's content from a store read without claiming, so the same reply can reach the model twice — once as the steered turn, once as the tool result — the seam's existing at-least-once property. The wait holds a turn for up to ten minutes, bounded by its own deadline and reclaimable by abort at any moment. What it bought: a blocked seat is a seat whose model is reasoning instead of sleeping; a refusal is learned in one poll interval; a timeout tells the model whether the peer ever saw the mail; and a reply the bridge already delivered ends the wait with its content instead of a false timeout.

## Testing

`packages/mailbox/tool-mailbox/tests/tool-mailbox.spec.ts` pins the schema shape and description contract, an already-queued reply (claimed, settled `done`, no duplicate), the refusal short-circuit returning inside one poll interval with the verbatim reason and ahead of unrelated queued mail, timeouts reporting delivered/never-picked-up/no-traceId, a mid-wait arrival waking the poll, a caller-signal abort settling an aborted error result promptly, the anonymous-run loud failure, the deadline clamp bounds, and card presentation. The read-based detection is pinned against the exact field failure: a threaded reply the bridge already settled `done` ends the wait with its content inside one poll interval and the row stays `done`; an unthreaded delivered reply ends it through the inbound-since fallback; a reply the bridge holds `claimed` is returned without disturbing its lease; inbound mail delivered before the awaited send does not end a traced wait; and a bridge-delivered mid-wait arrival ends an untraced wait. `mailbox_send` threading is pinned at the store: a reply published with `replyToTraceId` stores the awaited trace id and returns it as the result's correlation id. `packages/mailbox/local/tests/store.spec.ts` pins the enriched trace read (content fields, claim/delivery times, unreadable payload degrading to absence) and the inbound scan's address, floor inclusivity, state coverage, and ordering. The live user-level check ran the refusal and reply paths through real test-bed seats in a browser per the `dsh-user-testing` flow.
