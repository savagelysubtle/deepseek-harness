# 代理笔记：座席可以进行邮箱对话而无法伪造身份

Status: implemented

[English](2026-08-29-mailbox-seat-conversation-slice.md) | 中文

## 问题

投递邮件的发件人归属已单独修复（见邮件中继信封笔记），但在座席真正能够对话之前仍存在三处缺口。

**座席根本无法发送。** 进程内没有邮箱工具。`tool-cordis` 只是只读检查，且不在已发布的 bundle 中，因此座席唯一的发送路径是外壳调用 `dsh-mailbox send --from <任意> --to <任意>`。`--from` 是自由文本，所以座席可以伪造任何发件人，包括创始人。信封在接收端化解了这一点；但书写伪造的能力依然存在。

**存储无法为消息标注时间或建立关联。** `MailboxMessage` 不携带发送时间——sqlite 表有 `created_at`，却从未选入记录——因此中继按 `lease.claimedAt`（*投递*时刻）标注时间，任何排队等待的邮件都会被标错时间。而且无法按 `traceId` 查找消息，所以桥接无法确定一条来件是否在回答收件人自己发出的消息。这正是已目睹的 alfred/robin 故障的后半段：回复被读成了新指令。

**三条准入规则已声明却未强制执行。** `orgRegistryAllows()` 已导出、已充分测试，却没有任何非测试调用者，因此组织的 `edges` 与 `callUp` 形同虚设。除 `maxClaimPerCycle` 外没有任何回环防护。最严重的是，`~/.dsh/org/registry.yml` 在注释中声明"加载器必须拒绝任何跨越 test:true 边界的边，因此这些座席永远无法触及实时座席"——而 `test` 字段被解析、被类型校验，却在任何地方都未被强制执行。一次性测试座席可以触及线上生产座席。**没有代码支撑的承诺比没有承诺更糟，因为它会被依赖。**

## 决定

**发件人身份来自传输层。** 新的 `@deepseek-ai/dsh-tool-mailbox` 包注册两个工具。`mailbox_send` 接受 `to`、`subject`、`body` 和可选的 `blocking`——**没有 `from`**：运行时用启动器提供的可信会话名填充它，因此座席在物理上无法声称自己是另一个座席或创始人。`mailbox_check_inbox` **完全不接受参数**，因此座席只能排空自己的地址。匿名运行（无会话名）会在调用时让两个工具大声失败，而不是退回到不可信的身份。`dsh-mailbox` CLI 仍是外部操作者的引导路径，但会无条件将发件人标记为 `guest:<原值>`，无法抑制，也无法通过已带前缀的输入预先满足；被标记的发件人永远不匹配花名册座席，因此接收端将其渲染为 `unverified`。

**存储现在会标注时间并建立关联。** `MailboxMessage.sentAt` 为必填，由提供方在发布时从既有的 `created_at` 列铸造，且不会被 claim、reclaim 或 settle 重新标记——排队等待的消息保留其准入时间。新的 `MailboxPublishInput = Omit<MailboxMessage, 'id' | 'sentAt'>` 让两个由提供方铸造的字段都不在调用方可及范围内，与 `id` 已采用的纪律一致。`MailboxProvider.lookupByTraceId(traceId)` 返回 `MailboxTraceEntry[]`（`{ id, from, to, sentAt }`，最早在前），是一次纯读取：不 claim、不 settle、不修改任何内容——足以让调用方确定某个关联 id 是否曾经传递过以及方向如何。

**准入是有序的，且边界高于图。** 排空时的准入现在依次执行：注册表健康状况，然后是 `test: true` 边界，然后是组织拓扑，然后是发件人准入，最后是回环防护。标记为 `test: true` 的座席只能与同样标记的座席双向交换邮件，且该规则**高于准入列表、边列表和 `callUp`**——否则 `callUp` 座席会径直跨越它。拓扑拒绝会指明 `findOrgRegistryRoute` 提供的路由，从而告知发件人本应使用的路径。回环防护包括消息大小上限、按地址的深度上限、相同内容重复抑制，以及按 `traceId` 的跳数计数：只是防护，绝非支出上限；防护记忆只记录真实准入，因此被退回 pending 的租约会被重新判定，而不会被自己先前的检查所抑制。

## 考虑过的替代方案

**让发送工具接受 `from` 并加以校验。** 已否决。以什么为依据校验？唯一的权威是注册表，而一个本就可以合法地给任何同侪发邮件的座席，也就能把任何同侪指定为发件人。移除该字段是唯一没有绕过路径的版本。

**将缺失的组织注册表视为"拒绝一切"。** 对*缺失*的文件否决，对*损坏*的文件保留。缺失的注册表代表没有组织图的部署——即 CLI 引导场景——此时依赖注册表的规则无从判断，遂空操作。而存在却无法加载的文件会大声拒绝：没有任何检查能证明某次交换是边界安全的，而静默放行正是该边界要防范的失败。修好文件后，桥接会在下一个周期自愈。

**在回环防护之外再加支出上限。** 按创始人裁定明确排除在范围之外。防护阻止的是超大消息和自我重发的回环；它们对组织的总工作量不持任何意见。

## 后果

回复串联仍未渲染。它所需的接缝现已存在（`sentAt` 加 `lookupByTraceId`），但本轮刻意未触碰 `delivery.ts`，以便四条并行工作流保持互不重叠的文件归属。渲染"回复你于……的消息"是让一来一往读起来像一场对话、而非一串互不相干的指令之前，剩下的最后一块。

`MailboxMessage.sentAt` 成为必填对任何直接构造该记录的代码都是破坏性变更；仓库内的调用点已更新，发布方应使用 `MailboxPublishInput` 类型。
