# Agent Note: mailbox_await — 带截止时间的真实等待原语

Status: implemented

[English](2026-08-29-mailbox-await-tool.md) | 中文
## Problem

`blocking` 在邮箱消息上只是一个标记，不是机制：该接缝只发布了两个模型可见工具——`mailbox_send` 与 `mailbox_check_inbox`——完全没有等待原语。被要求"等回复"的席位只能临时拼一个 Bash sleep 轮询循环，每轮询一次烧掉一个回合；而当回复永远不来时，它会永远挂下去。实测：席位 A 向席位 B 发送阻塞消息，B 在回复中途被停止，A 轮询超过 2 分 27 秒——没有回复、没有错误、没有超时。

存储早已记录了等待所需的一切——已落定租约的 `deliveredAt`，以及（拒绝通知工作之后）经 `lookupByTraceId` 可达的被拒行终态 `failureReason`——但在发送者被阻塞期间，没有任何东西替它读取这些事实。

## Decision

`mailbox_await` 是同一挂载点上的第三个工具，采用与其他两个相同的 `mailboxAwaitTool(mailbox, identity)` 构造模式，并经同一条 `resolveMailboxIdentity`/`callerIdentity` 身份路径解析——不存在第二条身份机制。

- **关联走 `traceId`，回复穿透它。** `mailbox_send` 为每次发送铸造一个新关联 id，写入行、随结果返回并渲染进结果文本，模型由此持有句柄。await 的 `traceId` 参数即指向该 id；`lookupByTraceId` 取回该行的去向。方向选出被发送的行：记录的 `from` 等于调用席位自身地址的那一条——共享同一 id 的还有回复行与退信行，而那些是入站方向。send schema 携带 `replyToTraceId`：以被等待发送的 id 发布一条回复，即把它穿透到同一条链上（与退信路径相同的穿透方式），这让被追踪的等待匹配的是"那一条回复"而不是任何入站邮件。
- **回复检测靠读，认领是兜底。** 每个轮询先读再认领。桥——常规投递路径——会认领一条回复、把它拼接进等待席位的活跃回合、并把它落定 `done`；任何快于等待席位自身模型往返的回复都必然输掉认领竞态（实测 1.9 秒的回复对 3.4 秒才开始的等待），因此只认领的检测在每一条快速回复上都会超时，而答案就躺在对话里。`detectArrivals` 读取认领再也看不到的行：被追踪的等待优先取携带自身 trace、发往自身、处于 `done`/`claimed` 状态的行；取不到时回退到"自被等待发送准入以来的任何入站邮件"（未穿透的回复照样结束等待；无关入站邮件也会）；未追踪的等待读取自等待开始以来的入站邮件。读取不作认领与落定——`done` 行仍是桥的投递，新鮮的 `claimed` 行仍归持有其租约的消费者——所以同一条回复可能两次到达模型（拼接的回合与工具结果），这是接缝既有的至少一次投递性质。
- **拒绝中断等待。** 每个轮询先读被追踪行再认领；`state: 'failed'` 立即以记录的原因原文结束等待（信封不可读时给出口述的兜底原因）。被拒的发送绝不等满截止时间——拒绝在几秒内就已成定局，而那五分钟的悬挂正是本工具要消灭的东西。排在拒绝后面的无关邮件保持 pending，留给下一次排水。
- **超时陈述已知事实。** 到期返回普通结果而非错误，携带 `sentState`：`delivered`（附该行的 `deliveredAt`）、`claimed`（已被拾取、投递未落定）、`pending`（从未被拾取）或 `unknown`（无 `traceId`，或没有本席位发出的行）。"超时但 4 分钟前已送达"与"超时且从未送达"需要不同应对，结果把两样事实连同 `waitedMs` 一并交给模型。
- **全部截止时间算术跑在宿主时钟上。** `clampAwaitDeadlineMs` 在执行时把请求的截止时间解析到 1000–600000 ms 区间（默认 300000）；调用者从不提供剩余预算。下限存在的原因是：短于一个轮询间隔的等待根本观察不到等待中途到达的邮件；上限让单次占用的回合有界，且每次到期都把决定交还模型。工具不声明 `timeoutMs`，与姊妹工具一致——它自己的钳制截止时间就是边界。
- **轮询，而非忙等。** 两个 tick 之间睡 2 秒——低于桥自己的 5 秒排水周期，每 tick 只执行几条廉价的 SQLite 语句。不带 `traceId` 时，等待在该席位的任何入站邮件到达时结束，到期报告 `unknown`。
- **排队认领保留。** 仍处于 `pending` 的邮件按 `mailbox_check_inbox` 的方式排水——认领、把每张回执落定 `done`、返回相同的条目形状与渲染——这也让单席位 headless 世界照常工作：那里工具是唯一的读者，从没有桥来抢先。
- **可取消。** 等待把 `exec.signal` 透传给每一次存储读取和每一段睡眠；睡眠以中止原因拒绝并清除自己的定时器，被停止的席位在毫秒级收回控制权，取消结果由注册表的取消契约负责报告。

## Alternatives considered

- **只靠认领检测回复**——用户级测试实测失败后否决：桥赢得每一条在等待首次轮询之前落地的回复，这是确定性的，且已落定的行对认领不可见。基于读的检测无论哪个消费者赢了那行都看得到它；认领留给仍在排队的邮件，也留给无桥的单席位世界。
- **把穿透当作唯一的关联机制**——否决：检测不得依赖对端的配合，所以未带 `replyToTraceId` 发布的回复仍通过 inbound-since 兜底结束等待。穿透是其上的精度层，不是门槛。
- **围绕每个 tick 融合带超时的中止信号（`deadline()`）**——否决：等待不拥有超时分类，因为截止到期是结果而非错误；普通定时器加中止监听器是更小的机制，清理保证相同。
- **把 `claimed` 报告成"从未被拾取"**——否决：存储区分"已拾取未落定"，报成 pending 会把慢传输误诊为死传输。它以独立的 `sentState` 发布。

## Consequences

发送工具的模型可见 schema 长出了 `replyToTraceId`，其结果与渲染携带关联 id——对穿透的回复而言，那是被等待发送的 id 而非新铸的一个。穿透的对话在同一条链上累积跳数，因此桥的单 trace 准入上限（默认 8）约束一条链的长度，触顶时的拒绝会点名该 trace；更长的往来改挂到新的一次发送上。等待从存储读取中返回回复内容而不认领，所以同一条回复可能两次到达模型——拼接的回合一次、工具结果一次——这是接缝既有的至少一次投递性质。等待最多占住一个回合十分钟，由自身截止时间约束，且任何时刻可被中止收回。换来的：被阻塞的席位是模型在推理而非睡眠的席位；拒绝在一个轮询间隔内被知晓；超时告诉模型对端究竟有没有见过这封邮件；而且桥已投递的回复会带着内容结束等待，而不是给一个假超时。

## Testing

`packages/mailbox/tool-mailbox/tests/tool-mailbox.spec.ts` 钉住：schema 形状与描述契约、已在队列中的回复（被认领、落定 `done`、不重复）、在一个轮询间隔内带原因原文返回且优先于无关排队邮件的拒绝短路、报告 delivered/never-picked-up/no-traceId 的超时、等待中途到达的回复唤醒轮询、调用者信号中止后迅速以中止错误结果结算、匿名运行的响亮失败、截止时间钳制边界，以及卡片呈现。基于读的检测按实测失败场景钉死：桥已落定 `done` 的穿透回复在一个轮询间隔内带内容结束等待且该行保持 `done`；未穿透的已投递回复经 inbound-since 兜底结束等待；桥正持有 `claimed` 的回复被原样返回且租约不受扰动；在被等待发送之前投递的入站邮件不会结束被追踪的等待；等待中途被桥投递的邮件结束未追踪的等待。`mailbox_send` 的穿透在存储层钉死：带 `replyToTraceId` 发布的回复存储被等待的 trace id 并将其作为结果的关联 id 返回。`packages/mailbox/local/tests/store.spec.ts` 钉住富化的 trace 读取（内容字段、认领/投递时间、不可读载荷退化为缺失）与 inbound 扫描的地址、下限含端点、状态覆盖与排序。用户级活体检查按 `dsh-user-testing` 流程经真实测试床席位在浏览器中跑了拒绝与回复两条路径。
