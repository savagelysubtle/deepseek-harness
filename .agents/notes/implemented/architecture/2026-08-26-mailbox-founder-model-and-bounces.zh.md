# Agent Note：邮箱创始人模型——一切皆 steer、发送方标记 blocking、每次丢弃都退信

Status: implemented

[English](2026-08-26-mailbox-founder-model-and-bounces.md) | 中文

## 问题

Doc 1（外部议事席）发现三个耦合缺陷：紧急程度从错误的一方推断（`deliverToLive` 打断忙碌席位却对空闲席位排队——席位越忙、相同邮件越具破坏性）；一旦打断成为真实行为，中断的工作面临被渲染成空成功的风险；终态投递失败对发送方不可见（`unknown-address` 留下一行永远无人读取的持久失败记录）。

## 决策——经主席/创始人两次修订后的最终语义：

- **一切邮件均 steer 进活跃回合**（创始人修订，取代过渡期的发送方意图 `type:'steer'` 设计）：不推断忙碌度、不设基于类型的打断请求。传输层一视同仁地保证即时性。
- **`MailboxMessage.blocking?: boolean`**（默认 false）承载发送方的等待状态。它驱动接收方判断而非传输：阻塞型邮件渲染出可见的 `[BLOCKING]` 前缀，席位一眼可见同事/老板正卡在等待答复；其余均为 FYI 权重。不可信发送方风险仍由 facts-not-directives 投递加 fail-closed 的 `admitFromNamespaces` 排水门处理——不设 steer 白名单，那会违背创始人意图。
- **每个终态失败都退信**（议事席方案 (a)，普适采用）：路由失败会向原始 `from` 回发一条尽力而为的回复形通知，携带原 `traceId` 与原因。不退信之退信；不可解析的发送方不会得到伪造的目的地。适用于所有终态路径，包括此前静默的 `unknown-address`。（范围此后被准入管线工作及[耐久拒绝通知](../bug-fix/2026-08-29-mail-refusal-durable-sender-notice.md)收窄：一次准入拒绝——注册表健康、`test: true` 边界、组织拓扑、发送方准入、循环守卫——绝不存储退信，因为退信本身会受触发拒绝的那条规则约束。这些拒绝改为经 `mailbox/refused` 上下文总线报告，并把一条耐久通知记录进发送方会话。）

**席位别名花名册（组合缺口，同一变更）：** 桥此前假定所有目标 id 均由地址名称派生——这只对 headless 具名运行成立。`Config.seatAliases`（默认缺省）现在把经过文法校验的完整地址路由到一个既有会话 id，使 web 宿主席位会话与具名会话一样可 steer／可冷恢复。fail-closed：不从预设 persona 自动发现；主席的组合显式声明各行。

存储：SCHEMA_VERSION 由 1 升至 2 以加入 `blocking` 列（单调递增，旧文件按契约响亮拒绝）。CLI 收件箱条目暴露 `blocking`。apiproxy 的 `mailbox.publish` 线路接受并转发 `blocking`。

## 验证

桥套件：空闲与忙碌存活血席位均断言发生了 STEER（修订后测试 1–2）；边界拒绝的 steer 回退为排队准入；准入门不变；退信往返携带 traceId 与载荷原因（测试 5）；unknown-address 退信的普适性（测试 6）；无退信之退信、不为不透明发送方伪造地址。组合套件：生成中途发布的邮件在单个轮询节拍内被 STEER 进运行中席位（行在准入即 done），投递回合带归属且时序为 ['user','mailbox']，零退信行，持久转录中零 aborted 回合（S-2 证据：dsh 循环早已将被打断的回合记为 `aborted`，并将被中断的工具呈现为显式错误而非空成功）。

## 后果

主席到席位的派发完全告别排队（创始人传输规则：一律 steer）。紧急邮件能到达忙碌席位；常规邮件不再为他人的日程支付打扰税……两者同时成立，因为通道统一消除了时序依赖。等待答复的发送方现在拥有端到端可见的协议钩子。访客发送者可以被拒绝，但绝不再静默。
